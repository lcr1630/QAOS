The problem it dissolves

An acceptance criterion hides five guesses

It says what must be true. It does not say which user does it, from which state, with what data, on which environment, or what must not happen. A test written straight from an AC bakes in the author's guess about all five — and the guess is invisible in the resulting code.

FAILURE 01

Invisible guesses

Tests that pass on dev and fail on staging because an unstated assumption was baked in. The framework's answer: a structured interview makes every guess explicit before it becomes an assertion.

FAILURE 02

Standards drift

A style guide everyone agreed to and nobody follows six months later. The answer: standards live in tier modules, and an AI layer reads them at runtime — so the rule and the work never diverge.

FAILURE 03

"Was this tested?"

The honest answer is an anecdote, not a record. The answer: one identity spine joins issue → case → test → result, so the question becomes a query with an auditable answer.

Ownership model

Four tiers, segmented by responsibility

Not by headcount. One person can hold several tiers — the framework guarantees every responsibility has an owner, not that every tier has a dedicated hire.

T1
Core Director of QA
Company-wide standards, the tool stack, the shared AI skills & agents.
A change here changes every product line. The owner approves it; products never fork it.
T2
Manager QA Manager
Portfolio quality across ~3 products, the release gate, process definition.
Nothing ships without a recorded sign-off — auditable six months later, not a chat thumbs-up.
T3
Product Lead QA Product Lead
One product's real context, its suites, its case structure.
Produce suites an engineer can run without having to guess.
T4
Engineer QA Engineer
Running cases, maintaining specs, reporting evidence.
Report what actually happened. Nobody is hurt by an accurate red; everybody is eventually hurt by an inaccurate green.

Core sets the floor

A minimum every tier inherits — every test tagged, every skip explained, every created record cleaned up. A product cannot opt out.

Product sets the ceiling

A product may add what core does not impose — a second reviewer, a mandatory visual baseline, a stricter flake threshold. It may narrow, never relax.

The inheritance rule

Wanting to relax a core rule to ship something is the signal to stop and raise it with the tier owner — not to write an exception into a spec file. A rule that no product can satisfy is a broken rule, not a product problem. Fix it at the core.

Vendored flat copies under .claude/ — committed, pinned, refreshed via PR. No submodule step on a fresh clone.

PROPERTY 01

Vendored copies are committed

A fresh clone works with no build step. The diff after a refresh shows exactly what changed.

PROPERTY 02

Updates are opt-in per repo

base-version.json pins a version. Tracking the tip would let the release gate change underneath a team during a release.

PROPERTY 03

Lite updates via PR

Service engagements refresh the client's qa/ folder — reviewable, not silent.

PROPERTY 04

Never hand-edit a skill

Move the change into qa-framework-base, run base:refresh, commit the result.

The AI process layer

The mechanism that carries standards into the work

Skills and agents are how the standards reach the work, instead of sitting in a document nobody opens. The split is load-bearing.

Tier modules own the substance

Standards, release process, product context. The material each role is accountable for — the ownership boundary is the directory.

Skills & agents own the mechanism

They are thin. Each one reads from the tier modules rather than restating them.

A skill states process, not policy

If a skill contains a rule, that rule belongs in a tier module and the skill should point at it. Duplicated policy drifts, and the copy in the skill is the one that gets stale. A policy change lands in exactly one file and every skill picks it up on its next run.

Rule · the author never vouches

The requirement reviewer checks an artifact it did not write; the case reviewer reviews cases it did not draft; the bug reviewer re-runs a failure someone else reported. A review by the author is not a review.

Rule · context is contained

Browser-driving, result parsing, and data generation happen in a subagent's own context — so the orchestrating conversation doesn't carry that history forward and re-pay for it every turn.

Gates & the interview

The pipeline stops until a human says proceed

A gate is a full stop. Never skipped, never inferred from silence — an unanswered question is not a yes. Each gate has an explicit keyword that proceeds it, so approval is a deliberate act that leaves a record.

The interview is the cheapest place to find ambiguity

Cheaper than a case, a spec, and a run built on it. A fixed set of questions — which flows, which identity, what starting state, the happy path, the negative cases, the environment specifics, what's explicitly out of scope, and how each AC bullet maps to a case — and it refuses to infer an answer to make progress.

Steps are keywords, not prose

Prose has to be re-interpreted by whoever automates it, reintroducing the guessing the interview removed. A fixed vocabulary maps one-to-one onto the automation runner:

Navigate · Click · Fill · Select · Press · Upload · Verify

Shift-left evaluation

Push coverage down the pyramid — grounded in real source

E2E tests are the slowest, flakiest, most expensive coverage there is. This batch process finds cases that could be caught lower, classified by the lowest level that can still catch what they protect against.

VerdictThe case…Grounding required
UNITValidates an isolated function; no external dependencies; runs in millisecondsName the function and its file in real source, or it isn't a unit
INTEGRATIONValidates data flow between internal components; no full UIName the components and the seam between them
KEEP-E2EInherently needs a deployed environment or a real user journeyThe default whenever the evidence to shift is absent
PATH A

QA authors

Only when the logic is straightforward and the target repo is cleared. Produces a test + PR body as an artifact for a human to commit.

PATH B

Developer handoff

A backlog spec — evaluation, evidence, and acceptance criteria — for a developer with the architectural context.

KEEP

Stays E2E

Nothing changes. The case remains E2E, stated explicitly rather than by omission.

Two absolute rails

Automation never writes to application source. Path A vs B is about who authors — QA or a developer — never whether automation may push to app code. It never may.

Deprecation is conditional, never automatic. A shifted case is retired only after its replacement is green in CI — by marking state, never by hard-deleting. Until then, the E2E case is the only coverage there is.

The standards floor

Rules you don't relax to make something pass

This is the reference implementation's floor. Your team sets its own — but the shape generalizes, and the last one is a standing rule above all others.

01API-first state. Never drive the UI to set up data or log in when an endpoint exists.
02Injection over instantiation. Page objects and managers reach a test through fixtures — a constructed object skips teardown.
03Zero-trust locators. Role / label / test-id / text. A CSS nth-child chain encodes layout, and layout changes.
04Defensive waiting. Explicit visibility or a response wait. Never a fixed sleep.
05Mandatory tagging. Suite tag + feature tag + case-id. An untagged test runs, counts toward nothing, and looks complete.
06No silent skips. Every skip carries a reason; every deferred test carries an issue key.
07Clean up what you create. Teardown via API in afterEach / afterAll.
08Never weaken a test to pass. A test that can't pass honestly has found something. Stop and ask.
The standing rule

Automation has read-only access to the application's source control. It can open a PR in the test repository but never create, approve, or complete one against app code, a work item, or a pipeline run. Automation that can approve its own PR is not a QA tool.

Adoption path

How a team takes this and runs

Five moves from zero to running an issue through the chain.

1

Run the readiness gate (Lite)

Score testability before init. GO proceeds; CONDITIONAL scopes the plan; NO-GO delivers an eng checklist.

2

Install the harness

Lite: qa/ in the app repo. Standard: dedicated automation repo with vendored .claude/ copies.

3

Run the init skill once per product

qa-0-init interviews the adopter and fills every token — trackers, environments, credentials by reference.

4

Fill in product context

The highest-value, lowest-glamour file: real surface area, auth model, the parts that look broken and aren't.

5

Run an issue through the chain

qa-start → analyse → cases → manual → automate → report. Enable @core on PR; deliver Release Gate Lite.

Standards cascade down. Evidence flows up. A policy written once lands everywhere.

And the question the whole system exists to answer — was this tested? — comes back as a record, not an anecdote.
